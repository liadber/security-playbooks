# Design decisions

Each entry: what was chosen, why, and the trade-off.

## Server

- **Express 5 with zod.** Every body goes through one `validateBody` middleware that replaces `req.body` with the parsed value or answers 400 with one message per field; errors are `HttpError` instances turned into JSON by one handler. Each schema is tied to the shared contract with `satisfies z.ZodType<…>`, so a schema that drifts from the type fails typecheck. The trade-off is that routing, errors and auth are small hand-written pieces rather than a framework's conventions.
- **MongoDB with Mongoose, actions embedded.** A playbook is one document with its actions as an array of codes, because actions are only ever read with their playbook and never queried alone; Mongoose provides the schema, the indexes and typed documents. Actions are stored in one canonical order whatever order was sent, so equality and display never depend on the client. The trade-off is no catalogue table for actions, which is acceptable because the catalogue is a typed constant validated by zod.
- **Argon2id from `node:crypto`.** Passwords are hashed with the built-in Argon2id at the OWASP parameters; the parameters are stored in the hash and bounded when read back, so a tampered record cannot force an arbitrarily expensive verification. No native dependency has to be built. The trade-off is a Node floor of 24.7.
- **JWT with jose in an `HttpOnly`, `SameSite=Strict` cookie.** Login issues an HS256 token valid for one hour and sends it in a cookie with `Path=/` and a `Max-Age` equal to the token lifetime; `Secure` follows `COOKIE_SECURE`. The client never reads, stores or sends a token, so page scripts have nothing to steal. The trade-off is that the API serves same-site browser clients first: another client must keep the cookie itself, and with no refresh token a session ends after an hour.
- **404, never 403, for another user's playbook.** Every lookup is `{ _id, userId }`, so a foreign playbook, a missing one and a malformed id all answer the same 404; a 403 would confirm that the id exists. The id is checked before querying so Mongoose never throws on a malformed one. The trade-off is that a client cannot tell "not yours" from "gone", which is the point.
- **Case-insensitive unique name, enforced by an index.** A unique index on `{ userId, name }` with collation `{ locale: 'en', strength: 2 }` makes "Phishing" and "phishing" the same name for one user while other users may reuse it; the same collation sorts the list. The index rather than a find-then-save check means two concurrent creates cannot both succeed; a violation becomes a 409. The trade-off is that the duplicate-key error must be translated and the collation repeated on every query that should use the index.
- **Codes in the database, an options endpoint for the client.** Playbooks store codes such as `MALWARE_DETECTED`; the labels exist only on the server, typed as `Record<TriggerCode, string>` so a missing or extra code fails typecheck. `GET /playbooks/options` hands the codes, their labels and the name limit to the client, which hard-codes none of them. The trade-off is one more request per page load, in exchange for one place to add a trigger or an action.
- **PATCH for partial updates.** The update body is the create schema made partial and non-empty, so any caller may send one field or all of them under the same rules and the same 409. The app's form sends the whole playbook, which is simply a valid PATCH. The trade-off is that a partial body has more edge cases than PUT, which is why the empty body is rejected explicitly.

## Client

- **Dev proxy instead of CORS.** Vite forwards `/api/*` to the server with the prefix removed, so the browser talks to one origin, the server sets no CORS headers and the `SameSite=Strict` cookie works unchanged. The trade-off is that production needs the same arrangement, a reverse proxy or same-origin hosting.
- **React 19 form Actions through `useFormAction`.** Every form wraps `useActionState` through one hook that takes the submit function and returns the state (general error, per-field errors, kept values), the form action and `isPending`, turning an `ApiError` into field errors. Chosen values survive a failed submit, including multi-value fields; passwords never do. The trade-off is uncontrolled inputs, so a field that must reset is remounted through a key rather than driven by state.
- **`useApiData`, and a reload after every change.** Page data loads through one hook that numbers each attempt and ignores stale responses. After every create, save or delete the list is reloaded from the server rather than patched locally, because the server owns order, sorting and the canonical action order. The trade-off is one more request per change, in exchange for never showing a state the server would not.
- **Navigation lives in the route guards.** `ProtectedRoute` sends a visitor to `/login` and remembers the requested page; `GuestRoute` sends a logged-in user back there, honouring only in-app paths so the login page cannot serve as an open redirect. Pages never call `navigate()`: after login, logout or an expired session (any 401 clears the user) the guards react to the auth state. The trade-off is that navigation follows from state changes rather than from an explicit call at the site of the action.
- **Feature folders with one-way dependencies, and a folder per component.** `app/` may import `features/` and `shared/`; a feature imports only `shared/` and never another feature; `shared/` imports neither, and test files follow the same rule. Cross-folder imports go through the `@/` alias. Both pages need the playbook options, so that loader lives in `shared/options` rather than in the playbooks feature. Every component with more than one file (its CSS Module, its test) has its own folder with an `index.ts` that only re-exports it, so imports read `@/shared/components/Button`; single-file components and non-component files stay at the root of their folder. The trade-off is that a piece two features share must move to `shared/` even when only those two use it, and every component folder carries one extra file.
- **`SidebarLayout` as a compound component.** `SidebarLayout`, `SidebarLayout.Sidebar` and `SidebarLayout.Main` live in one file; each part is placed with CSS `order`, so the JSX order does not matter, the React counterpart of multi-slot content projection. Both pages compose it with a form in the sidebar and a titled main area. The trade-off is that slots are less discoverable than named props, in exchange for holding arbitrary content.
- **Desktop-only flexbox layout.** The shell fills exactly the viewport (`100dvh`, a flex column with `min-height: 0` down the chain), so the header and the section titles stay put and only the sidebar and the main content scroll. There are no media queries and no CSS Grid: the app targets desktop screens by design. The trade-off is that it is not adapted to phones.
- **CSS variables, no magic numbers.** Every value a stylesheet uses is a variable in `variables.css`; the only literals are `0`, `100%`, `100vh` and `100dvh`. Units are `px` for borders, outlines and radii and `rem` for everything else. The trade-off is that a few values used only once still get a name.

## Project

- **A type-only contract in `shared/types`.** Request and response shapes live once as `.d.ts` files that both sides import with `import type` through `@shared/*`, so nothing at runtime depends on the folder. Values stay on the side that enforces them: the client repeats only the password minimum and reads the name limit from the options endpoint. The trade-off is that a value both sides need must be duplicated or served.
- **Tests next to the code.** Server: Vitest, with supertest against the real app on an in-memory MongoDB from `mongodb-memory-server` (one database per test file) and unit tests for config, hashing, tokens and schemas. Client: Vitest with Testing Library in jsdom, the API modules mocked, queries by label, text and role, the way a user finds elements. The trade-off is that the first server run downloads a MongoDB binary, and page tests do not exercise the server's real responses, which the server tests cover.
